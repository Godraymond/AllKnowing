# Recordly fork (Godraymond/AllKnowing)

This fork is based on the official Recordly **v1.4.0** release line (upstream commit `4992686`), not on upstream `main`.

## Don't

- Don't merge or pull upstream `main`. Upstream replaced it with a 2.0 rewrite whose history split from 1.4.0 in Nov 2025, so a merge drags in a different codebase.
- Don't use GitHub's "Sync fork" button, for the same reason. It offers to throw away this fork's commits.

## Day to day

- Work on `main`. Every push to `main` runs the **Code Quality** workflow (typecheck, lint, tests).
- Check before pushing: `npx tsc --noEmit && npm run lint && npx vitest --run`
- Headless/cloud setup: `ELECTRON_SKIP_BINARY_DOWNLOAD=1 npm ci --ignore-scripts`. The app window needs a desktop. On Windows, run `npm run dev` from a normal path; a path under a virtualised AppData folder breaks Vite's transform and gives a blank window.

## Releases

1. Bump `version` in package.json (`npm version patch --no-git-tag-version`), commit, push.
2. Run the **Build installers** workflow (Actions tab → Build installers → Run workflow). Cloud sessions can't start it themselves (the API refuses workflow dispatch and the git proxy refuses tag pushes), so use the person's browser or ask them to press it.
3. It builds Windows (.exe), macOS (Intel and Apple Silicon .dmg/.zip) and Linux (.AppImage) and publishes them as GitHub release `v<version>`.

Installed copies check this fork's releases for updates (`publish` in electron-builder.json5). Builds are unsigned, so Windows SmartScreen and macOS Gatekeeper warn on first open, and macOS auto-update won't work without signing.

## The AllKnowing assistant (`assistant/`)

`assistant/index.html` is the meeting assistant: prep plan, live transcript with "what to say next" and a visual summary, minutes, follow-ups, Outlook calendar holds and email drafts. Its Import screen takes transcripts recorded elsewhere (.txt/.srt/.vtt/.docx/.json, pasted text, or a Teams meeting's transcript) and runs them through the same minutes and follow-ups. Served by the Mac mini it also takes the recording itself (mp3, m4a, wav, mp4…), see "Recordings" below. It runs as a claude.ai artifact, not inside the Electron app, because it relies on the artifact runtime: `dictation` (speech-to-text), `sample` (Claude), `db` (per-user storage), `mcp` (Microsoft 365: `outlook_calendar_search`, `outlook_create_event`, `outlook_create_draft`, `read_resource` for Teams transcripts), `downloads` and `user`.

- Live artifact: https://claude.ai/artifact/RLztYbj7DvF4Lm11eekJtd (slug `c5262278-7a8f-4515-8ac2-01b1c8e8d93e`).
- To change it: edit `assistant/index.html`, run `npx biome lint assistant/index.html`, then republish that file to the same artifact. Keep the repo copy and the artifact in step.
- If the page starts calling a connector tool it hasn't used before, add the tool to the artifact's declaration first (read_declaration, then declare_capabilities with the whole declaration), then republish.
- Don't republish while the owner is in a live meeting: open copies of the page reload at their next quiet moment.
- Outlook writes (Nov 2026): Add to calendar (`outlook_create_event`) and Draft it in Outlook (`outlook_create_draft`) need the connector's write permissions, `Calendars.ReadWrite` and `Mail.ReadWrite`, which a Microsoft Entra Global Administrator has to approve for the tenant (Claude's support article "Set up the Microsoft 365 connector"; on Team and Enterprise plans an owner also allows the write tools in Organization settings → Connectors). The owner's tenant had only the read set, so Outlook answered 403 "Missing scope". When a write is refused (`writeRefused`), the form says so in plain words with how to fix it (`writeFixEl`) and offers what needs no permission: Outlook on the web's new-event or new-email form with everything filled in (`outlookEventLink`, `/mail/deeplink/compose`), a calendar file (`icsFile`: UTC times, escaped text, lines folded at 75 bytes), or the email app (`mailto:`); on a phone the file and the email app come first (`showWays`). The refusal is remembered until a reload (`noWrite`). Without the connector (the web app, the Mac mini) the same forms open with only those ways ("Email it" in place of "Draft it in Outlook"). Other Outlook errors are shortened to what Outlook said (`outlookSaid`). Check: `node assistant/check-outlook.cjs` (takes those pieces out of the page by name).
- Meetings only since Nov 2026: 狼人杀 (seat tracking, game prompts, boards) was taken out at the owner's request. Old game records (`mode: "werewolf"`) stay stored but `shown()` keeps them off every list, and the last-opened one isn't reopened.
- Mind map and key quotes (asked for after the owner saw another tool's live summary and quote highlights). The live picture's `discussed` (topics and their points), decisions, open questions and actions are drawn as a mind map (`mapOf`, `mindMapEl`: plain boxes and CSS lines), which took the place of the old "So far" list on the Live screen. It answers to the width of its own box (a container query on `.mm-wrap`): left to right where there is room, standing upright in a side column or on a phone, so nothing needs swiping. The live update and the minutes also return `quotes: [{who, quote, why}]`, shown as "Key quotes" live and "Highlights" in the minutes. A quote is shown only if its words are in the transcript (`saidQuotes`: capitals, spaces and punctuation aside; typed notes don't count), and the line they are on decides whose they are (`who` is a name, or `vN`, which `quoteWho` turns into the voice's name); Claude is told this in `QUOTE_RULE`, and `node assistant/check-quotes.cjs` tries that function on a made-up meeting (it takes it out of the page by name, so keep it between `bareWords` and `normMeetingLive`). The minutes return `topics` for their own map (older minutes fall back to the last live picture, then to their key points). Both go into the downloaded minutes. The live transcript already shows words as they are spoken (`onPartial`).
- Starting a meeting (Nov 2026, the owner asked for it): the first time the Live screen opens for a meeting that hasn't started, the page asks "Start recording?" (`askToRecord`, once per meeting per page load; never for imports or a meeting already listening). It says that it keeps the transcript, not the audio, and to tell the room; Start recording calls `startListening()` straight from the click, which `dictation.start()` needs. Where this window can't listen it says why instead. claude.ai gives the page no dictation at all outside a Chromium browser tab and the desktop app's main window, and can't say why, so `noListenWhy()` reads the browser (iPhone/iPad, the Claude app, Safari, Firefox, or a window it isn't offered in) and the same words go in the prompt, the Live banner and the Start listening toast. The web app's own reason (`dictation.unavailable`, e.g. a link that isn't secure) wins over it.
- Voices: the web app's listener (below) also says which voice spoke, so its lines carry `v`. A voice gets a name from a tap on a name chip while it talks or on a line's tag, or from Claude (`m.voices`, asked for as `voices` in the live update when any line has a voice). Voice numbers restart on every connection, so each listening start and each reconnect gets its own block of 20. With no `v` on any line (the artifact) none of this runs and Claude's prompts are unchanged.
- The page can't transcribe audio files itself, and nor can Claude through `sample` (text and images only). On the Mac mini the Import screen hands the recording to the hub, which turns it into text itself with free speech models (see "Recordings on the Mac itself"), or has Soniox do it when that's asked for. Elsewhere, the desktop app's **Transcribe a Recording…** (`electron/transcribeRecording.ts`; taskbar Jump List on Windows, Dock menu on macOS, tray on Linux, File menu everywhere) runs the bundled whisper.cpp locally and saves `<name>.transcript.txt` and `<name>.srt` for the Import screen.
- Data lives in the artifact's db under `data/users/<id>/home` (settings), `.../home/index/<id>`, `.../home/meetings/<id>` with transcripts in `.../meetings/<id>/parts/pNNN`, and `.../home/todos/<id>`.
- **Download all notes / Bring in notes** (Home → Settings): one JSON file (`kind: "allknowing-notes"`) with every meeting (its `segs` included), every follow-up and the settings. Bringing one in writes meetings as they are (their own `updatedAt`) and skips any already there with the same or a newer `updatedAt`, so it can be repeated. It's how notes move between claude.ai, the web app and the Mac mini, and it's the Mac mini's daily backup format. A notes file added on the Import screen is offered here instead of being read as a transcript.

### The web app (iPhone and any browser)

The same page also runs outside claude.ai, so it can be opened in a browser or installed on an iPhone (Safari → Share → Add to Home Screen). An artifact can't do this job: its frame has no microphone, and its `dictation` gives no voices.

- `assistant/build-web.cjs` writes `assistant/dist/`: `index.html` with the manifest, icons, iOS tags and `web/standalone.js` added in `<head>`. `index.html` in the repo stays exactly what the artifact runs.
- `assistant/web/standalone.js` provides `window.claude` when the artifact runtime isn't there (and on the Mac mini, see below): `sample` (Claude, either through the Mac relay below or the Anthropic Messages API with the user's own key, streamed), `dictation` (microphone → 16 kHz 16-bit mono → Soniox real-time WebSocket with speaker diarization → `onFinal({ text, voice, gap })`), and `downloads`. No `db` or `mcp`: meetings live in that browser's localStorage, and Add to calendar and the follow-up email open Outlook on the web, a calendar file or the email app instead of writing to Outlook. Keys are stored on the device only (`allknowing:keys:v1`).
- The Soniox protocol was taken from its official SDK (`@soniox/client` 2.5.0): `wss://stt-rt.soniox.com/transcribe-websocket`, key in the WebSocket subprotocol list (`["soniox-api-key", key]`), one JSON settings message, binary audio frames, `""` to finish, `<end>`/`<fin>` marker tokens, `{error_code, error_message}` on failure.
- **Claude on the user's Mac** (`assistant/relay/`): `relay.cjs` is a small Node server on the Mac that answers a subset of the Messages API (`POST /v1/messages`, streamed SSE, `GET /health`) by running `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --tools "" --strict-mcp-config --no-session-persistence ...` once per request, so Claude runs on the user's Claude plan through Claude Code itself (Anthropic's docs: `claude -p` signed in with a plan draws from the plan's limits). It strips `ANTHROPIC_API_KEY` from Claude Code's environment, listens on 127.0.0.1:47823 only, needs the pairing code as `x-api-key`, and only allows CORS from the Pages origin and localhost. `install.sh` (run on the Mac via curl | bash) sets up the files, a LaunchAgent and `tailscale serve --bg --https=8443`, and prints the Mac link `https://<mac>.ts.net:8443/#<code>` that the phone pastes in "This device". The message shapes come from the Agent SDK's types (`@anthropic-ai/claude-agent-sdk` 0.3.325) and the flags from `claude --help` (2.1.325); the relay leaves out any flag its Claude Code doesn't list and retries without one it rejects. Checks: `node assistant/check-relay.cjs` (with `relay/fake-claude.cjs` standing in for Claude Code) and the Mac section of the web app test. The installer was dry-run on Linux with stand-ins for launchctl, tailscale, plutil and pbcopy, never on a real Mac.
- Hosting: the **Web app** workflow builds on every push that touches `assistant/` and force-pushes the result to the `gh-pages` branch. GitHub Pages serves it at https://godraymond.github.io/AllKnowing/ once Pages is on (Settings → Pages → Deploy from a branch → `gh-pages`, `/ (root)`). Cloud sessions can't change that setting.
- Not testable from a cloud session: a real iPhone, a real microphone, the real Soniox service, the real Anthropic API, a real Mac (mini) with Tailscale and launchd, and real `claude -p` (running it here is blocked). What is tested is the page in headless Chrome with a fake microphone against local stand-ins that follow the SDK's protocol.

### The Mac mini (`assistant/hub/`)

The owner's always-on Mac mini is the home for AllKnowing: it serves the web app, keeps every meeting for all devices, and keeps the keys. Setup guide for the owner: `assistant/hub/README.md`.

- `hub/hub.cjs` (Node 18+, no dependencies) serves `~/AllKnowing/app/` and injects `<meta name="allknowing-hub">` into `index.html`; `standalone.js` sees it and switches to hub mode: `db` and `user` (id `owner`) over the hub's API, `sample` through `POST /v1/messages` (the hub adds the Claude key it keeps), and listening with a one-use Soniox key from `POST /api/speech-key` (Soniox `POST /v1/auth/temporary-api-key`, `single_use`, 60 s, from `@soniox/node` 2.5.0) for every connection. Keys never reach a device; the Mac mini box on Home saves them (`PUT /api/keys`).
- Notes: one JSON file per document under `~/AllKnowing/notes/<path>.json`, same paths as the artifact db (`data/users/owner/home/...`), also held in memory. `GET/PUT/DELETE /api/db/doc?p=`, `GET /api/db/col?p=&order=&dir=&limit=`, and `GET /api/db/watch` (server-sent events: `{p}` for each change, `{app}` after a page update) so open lists follow other devices. The runtime reads it with `fetch` (needs the code header) and re-reads a list on each change, on reconnect and when the page comes back to the front.
- Who may ask: the pairing code (`x-api-key`) on everything but `/api/hello`. This Mac's own browser (`localhost`/`127.0.0.1` Host, from loopback, without `X-Forwarded-For` or Tailscale headers) gets the code from `/api/pair/local`. 12 wrong codes from one client (by `X-Forwarded-For` behind Tailscale Serve) lock it out for 10 minutes. `#pair=CODE` in the address pairs a device.
- Microphone: only https or localhost may use it. Tailscale Serve gives `https://<mac>.<tailnet>.ts.net`; plain `http://<mac>.local:4790` at home works for everything but listening, and the page says so (`dictation.unavailable`, error code `insecure`).
- `~/AllKnowing`: `config.json` (mode 600: port 4790, host, code, `claudeKey`, `speechKey`, `tsName`, `lanName`, `autoUpdate`, `keepAwake`, and for recordings `longFiles`, `fileModel`), `notes/`, `backups/` (`AllKnowing notes YYYY-MM-DD.json`, daily, last 30), `recordings/` (one folder per recording while it's turned into text), `speech/` (the free speech engine and models, about 2.1 GB), `app/`, `hub/hub.cjs` and `hub/speech.cjs`, `logs/hub.log`. `localSpeech: false` in config.json switches the free models off. On macOS it runs `caffeinate -is -w <pid>` so the Mac stays awake.
- `hub/install.sh` (Mac, `curl | bash`; `uninstall` keeps the notes): finds Node, downloads the app, `hub/hub.cjs` and `hub/speech.cjs` from the gh-pages branch checking each file against `version.json`'s SHA-256, writes `config.json` (keeps code and keys), runs `tailscale serve --bg --https=443` (8443 if 443 is taken by something else) when Tailscale is connected, and installs the LaunchAgent `com.godraymond.allknowing` (KeepAlive). `AK_HUB_TEST=1` lets it dry-run off a Mac with stand-ins for launchctl, plutil, scutil, pbcopy and tailscale.
- Updates: `build-web.cjs` writes `dist/version.json` (version, `hubApi`, every file's SHA-256) and `dist/hub/`. The hub swaps in new page files by itself every 6 hours when nothing was saved for 15 minutes and `hubApi` allows; **Get the latest version** (`POST /api/update`) also replaces `hub.cjs` and `speech.cjs` (both checked with `node --check` first, the old ones kept as `.previous`), and exits for launchd to restart it. Raise `HUB_API` in both `build-web.cjs` and `hub.cjs` when the page starts needing something new from the hub.
- Check: `node assistant/check-hub.cjs` (stand-ins for Claude, Soniox and GitHub; pairing, keys, proxy, one-use keys, notes and watch, backup, restart, updates). It and `check-recordings.cjs` run the hub with `AK_HUB_SPEECH=off`. The page side of hub mode is in `check-web-runtime.cjs`.

#### Recordings (the Mac mini turns them into text)

Only the hub can do this (it has the models and the Soniox key, and can run for an hour with no page open), so `cap.transcribe` exists only when `standalone.js` runs in hub mode; the artifact runtime is never asked for it. There are two ways, and a job carries which (`engine`): `local`, the Mac's own free speech models, used whenever they're ready; and `soniox`, used when it's asked for ("In a hurry? Use Soniox instead") or when the models aren't there. `cap.transcribe.ways` tells the page what's available. The rest of this section is common to both, then Soniox; the free models have their own section below.

- The page (`importRecording`): `transcribe.send(file)` sends the file in pieces (`POST /api/transcribe` → `PUT /api/transcribe/<id>/data?at=<offset>`, carrying on from the `received` the hub answers → `POST …/start`). Then it makes the meeting with `status: "transcribing"` and `job: { id, minutes }` and goes to it. Whichever device has that meeting open (`watchJob`) asks `GET …/<id>` every few seconds, and when it's `done` takes the text (`POST …/claim`, one page at a time; a second page waits for the saved copy), saves it as the transcript (lines carry `v`, the voice number), marks the meeting `done` with `transcribed: { by, model, joins }`, drops the job (`DELETE`), and writes the minutes if they were asked for. So the device that sent the recording can be closed.
- Voices get names from the minutes: whenever lines have `v`, the minutes prompt asks for `voices` too (`applyVoiceNames`), for live meetings as well. A tap on a name in the transcript changes it.
- The hub (`hub.cjs`, "recordings"): one folder per recording in `~/AllKnowing/recordings/<id>/` (`job.json`, the audio, parts, `result.json`), one job at a time, the rest queued; jobs carry on after a restart. The audio is deleted here and at Soniox as soon as the text is back; the text when a page has saved it, or after a week. Stopping a job drops it here and at Soniox, and for that the hub has to know what Soniox holds: the request that asks for a transcription is never cut off, and an upload that has gone in full waits for its answer, because the answer carries the id to delete (cut off at that moment, a transcription was left behind at Soniox).
- Soniox's file API as `@soniox/node` 2.5.0 calls it: `POST /v1/files` (multipart), `POST /v1/transcriptions` (`file_id`, `enable_speaker_diarization`, `language_hints`, `context`), `GET /v1/transcriptions/<id>` until `completed`, `GET …/transcript` (tokens with `start_ms`, `end_ms`, `speaker`), `DELETE` both. The model is the newest non-preview `async` one from `GET /v1/models` (`stt-async-v6` if that can't be asked; `fileModel` in config.json overrides).
- How long a file Soniox takes isn't settled: its limits page says 60 minutes, its error page 300. The hub tries a long recording whole first; if Soniox refuses, it goes in parts of 57 minutes that overlap by 4, and `longFiles` in config.json remembers which way worked. In the overlap both parts heard the same words, which matches the voices across the join and gives a quiet moment to cut at; `joins` in the result says where, and the page tells Claude (a voice silent around a join gets a new number).
- Reading and cutting needs nothing installed for MP3, WAV, ADTS AAC and AAC/MP3 inside MP4/M4A/MOV (a video goes as its sound only, as an ADTS file). Other kinds go whole when they fit; when they have to be cut, `ffmpeg` (if installed) or macOS's `afconvert` makes a 16 kHz mono WAV first.
- Checks: `node assistant/check-recordings.cjs` (recordings made up in the check with a counter in their sound, a stand-in for Soniox that "hears" a script from that counter, stand-ins for ffmpeg/afconvert; whole and in parts, every format, errors, restart, queue, clean-up), and the page side in `check-web-runtime.cjs`. Not testable from a cloud session: the real Soniox file API (which limit it has, its error wording, how it numbers speakers), and the real `afconvert`.

#### Recordings on the Mac itself (free speech models, `hub/speech.cjs`)

`HUB_API` 3. The owner asked for recordings to cost nothing, the way dropping an MP3 into a Claude chat does (there, Claude's sandbox runs free models). The Mac mini is AllKnowing's computer, so it runs them: no audio leaves it and nothing is paid.

- Engine: sherpa-onnx through its Node package `sherpa-onnx-node` 2.0.1 (prebuilt for darwin-x64, darwin-arm64, linux-x64, linux-arm64), fetched from npm as tarballs, not installed with npm. Models from the sherpa-onnx GitHub releases. Every download has its size and SHA-256 written in `speech.cjs` (`ENGINE`, `MODELS`) and is only used if it matches. They go in `~/AllKnowing/speech/{engine,models}`; `ready.json` there marks a set-up that passed its try-out, `speeds.json` holds this Mac's measured speeds.
- The hub (`hub.cjs`, "on this Mac for free"): `startSpeech()` at start-up (ready at once if `ready.json` matches, else `setupSpeech()` fetches what's missing with resumable downloads, unpacks with `tar`, then runs `node speech.cjs check`). State in `status().local` (`none`, `getting`, `checking`, `ready`, `error`, `off`) with progress; `GET /api/speech`, `POST /api/speech/setup` (the card's Try again). `AK_HUB_SPEECH=off` turns it off (the other checks use this, or they would start a 1.8 GB download); `AK_HUB_SPEECH_SOURCE` and `AK_SPEECH_CATALOGUE` point it at stand-ins.
- A local job (`localJob`): the recording becomes `sound.wav` (16 kHz mono, by ffmpeg or macOS's afconvert; a video's sound is pulled out first by the hub's own MP4 reader), then `node speech.cjs run <job folder> <speech folder>` runs at low priority and reports `{step, progress, left}` lines, which `jobStatus` passes on (`engine`, `stage`, `progress`, `left`). Stopping a job or the hub kills it; a restart carries on from the step files. `POST …/start {engine}` sends a failed job the other way, from scratch.
- `speech.cjs` steps, each in its own process so a model's memory is given back: **first** (Silero VAD finds the speech; SenseVoice hears each stretch and names its language), **second** (stretches joined into pieces of up to 16 s in one language; Parakeet TDT v3 hears Latin-script pieces, Paraformer hears Chinese), **judge** (Qwen3-ASR 0.6B hears every piece, with the meeting's names as hotwords; `ask.quick` limits it to pieces the first two differ on), **voices** (pyannote segmentation 3.0 and CAM++ embeddings, clustering threshold 0.75, 90 minutes at a time with `joins` where blocks meet), then `assemble`.
- Settling (`settle`): texts are compared as units (a word, a Chinese character, a number) with spelling differences folded out (capitals, Traditional/Simplified through an OpenCC table, "fifty"/"50", "九点"/"9点", "百分之十五"/"15%", -ise/-ize). The lead model's wording is kept (Parakeet for Latin script, SenseVoice for Chinese: they give punctuation and word times). In each place the models differ, the most votes win; a model whose whole text is unlike the others (wrong language) is dropped. For Chinese the judge has two votes, because SenseVoice and Paraformer are one family and make the same slips; for English it has one, so Parakeet and SenseVoice agreeing outvote it. With no majority the most trusted reading is kept and the rest go in the line's `alt: [[start, end, [readings]]]`.
- The page: lines keep `alt`; `segEl` underlines those words (a tap says what else was heard); `txLines` shows Claude `{kept / other}` in place with `DOUBT_NOTE`; `m.transcribed.by` is "Mac mini" or "Soniox"; `jobLine` shows the step and percentage.
- How well it does, measured here on a 2-core Linux machine with the real models (made-up meetings read by text-to-speech, clean and with room noise and MP3 compression): about 1 to 2% of words wrong in English and in Chinese after settling, against 2 to 9% for the fast models alone; the mixed English/Chinese meeting came out in both languages. Five minutes of a real speech took three and a half minutes. Voices were right about 80 to 90% of the time on the made-up meetings. Real meetings will be worse than this.
- Checks: `node assistant/check-speech.cjs`, with `check-speech-engine.cjs` standing in for the engine (its "sound" carries the time each sample was said, and a script says what each model hears): settling, the steps, resuming, the hub fetching and checking downloads, a recording through the hub, stop, restart, failure and the choice of way. Not in CI, because the models are 2 GB: the real engine and models (tried by hand on Linux x64). Not tried anywhere: the engine's macOS builds (its Intel build's `.node` is marked for macOS 15, though it only uses long-standing system calls), real `afconvert`, and a real Mac's speed.
